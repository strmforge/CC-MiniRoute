# CC MiniRoute 3.19.3-rc1 测试版

这次不是简单地在界面上多放一个账号列表，而是把 Codex 多账号真正接到了请求出口上。

以前 CC Switch 虽然能登录多个 ChatGPT 账号，但真正发请求时仍然主要依赖当前默认账号。额度用完后，长任务还是可能停下来，用户还得手动换账号。这个版本补上了后半段：账号可以进入本地账号池，由 CC MiniRoute 按规则选择可用账号，并在遇到登录失效、限流或并发占满时暂时跳过有问题的账号。

## 最直观的变化

固定的 `OpenAI Official` 卡片现在有三种用法：

1. **使用 Codex 官方登录**：完全沿用 Codex 自己的登录态和官方额度，不走 CC MiniRoute 托管账号。
2. **固定账号**：从已登录或已导入的账号里指定一个，所有请求都用它。
3. **账号池**：把启用的账号交给 CC MiniRoute 调度，适合长任务和多个自有账号。

不用再额外新建一张重复的 `codex_oauth` 卡片。以后想回官方登录，直接把这张卡片切回“使用 Codex 官方登录”即可。

## 这次具体补了什么

- 可以用 Device Code 正常登录多个 ChatGPT 账号。
- 可以批量导入 JSON、JSONL 或文本格式的账号凭证。
- 导入已存在的账号时可以更新资料，并保留仍然有效的 refresh token。
- 每个账号可以单独设置启用状态、是否加入账号池、优先级、并发上限、到期自动暂停和独立代理。
- 账号池会优先使用优先级更高且还有并发余量的账号。
- 遇到 401、403 或 429 时会让对应账号进入冷却，后续请求可以绕开它。
- 同一段 Codex 会话会尽量粘在同一个账号上，减少上下文归属错乱。
- 转发到官方 Codex 上游时会带上正确的 `chatgpt-account-id`。
- access token 和 refresh token 不会通过公开接口返回，也不会写进普通日志。

## 官方登录不会被覆盖

这是本版专门处理的一点。

- 选择“使用 Codex 官方登录”时，配置使用 `requires_openai_auth = true`，Codex 继续读取自己的登录态。
- 选择固定账号或账号池时，凭证只在 CC MiniRoute 本地代理发送请求前注入。
- 两种模式都不会覆盖 Codex 的 `auth.json`。
- 取消托管账号绑定后，会恢复 Codex 原生官方登录模式。

也就是说，官方额度和托管账号不再是只能二选一且难以回头的两套配置，而是同一张官方卡片里的三种明确模式。

## 关于批量导入和自动续期

能否自动续期取决于导入内容：

- 通过正常 Device Code 登录、并持有有效 refresh token 的账号，可以自动刷新 access token。
- 只有 access token 的账号可以使用，但过期后不能凭空续期，界面会明确显示需要重新认证。
- 批量导入不会把 refresh token 回传到前端列表或普通日志。

## 还需要大家帮忙测试的部分

这个版本标记为 `rc1`，主要因为真实世界里的账号状态比测试数据复杂。最需要反馈的是：

- 多个真实订阅账号连续运行时，额度耗尽后的切换是否顺畅。
- 401、403、429 冷却后能否按预期恢复。
- 不同地区、不同代理和不同套餐下，`chatgpt-account-id` 是否都能正确匹配。
- 旧版本已有 Codex OAuth 账号升级后是否能正常迁移。
- 固定账号、账号池和官方登录来回切换后，历史会话是否保持一致。

请先在非关键任务上试用。反馈问题时可以提供版本号、操作步骤和脱敏后的错误信息，不要上传 access token、refresh token、API Key 或完整本机配置。
